# 坑库

> 按**症状**查。每条四段：**症状 → 真因 → 修法 → 证据**。
> 只写"已修复"没有证据 = 白写，所以每条都留了可复现的数字。

---

## 首条（命中率最高，先看这个）

### 坑 01 · 成片一片白，零报错，所有判据全绿

| | |
|---|---|
| **症状** | 渲染"成功"，帧数对、时长对、亮度统计"正常偏高"，**画面是白的** |
| **真因** | 工程里有一个**起播遮罩**（用来盖住字体加载/初始化期的闪烁）。渲染时它没被隐藏，于是每一帧都盖着它 |
| **修法** | 渲染前显式调一次隐藏；并把它写进 `trial.js` 的 `MASK` 红线（**判据化**，不靠记性） |
| **证据** | 灰度统计在"白屏"和"正常浅色画面"上区别很小 —— **所以亮度判据抓不到它**。只有抽帧看图才发现 |

> **教训**：遮罩/加载态这类"临时视觉层"，如果在渲染链路上没有**结构性**的关闭点，
> 它一定会以"零报错"的方式进成片。

## 一、时间轴与合成

### 坑 02 · 用了 `-shortest`，末尾画面静止而人声还在念

| | |
|---|---|
| **症状** | 片子末尾约 0.12 秒，画面不动了但配音还在播 |
| **真因** | `ffmpeg -shortest` 在音视频时长不等时，会**按较短的那个截断** —— 而 PNG 序列比音频短了几帧 |
| **修法** | 别用 `-shortest`。时长显式对齐（`-framerate` + 序列帧数 == 时长×fps） |
| **证据** | 实测 **349 帧 vs 353 帧**，差 4 帧（BUG-2328） |

### 坑 03 · 想导 2 秒的片段，出来了 300 帧

| | |
|---|---|
| **症状** | 指定时长后，导出的是整片长度 |
| **真因** | 导出函数的参数**没被消费** —— 它内部永远读全局的 `__dur` |
| **修法** | 让导出函数接受 `opt` 覆盖（`dur` / `fps` / `name`），并**回读断言**实际用的值 |
| **证据** | 12s × 25fps = 300 帧。想导 2 秒却得到 300 帧 = 参数完全没生效 |

### 坑 04 · 视频画面"稳定慢半拍"

| | |
|---|---|
| **症状** | 动效是对的，视频比它晚一点点；每帧都晚同样多 |
| **真因** | `video.currentTime = x` 是**异步 seek**。赋值返回时那一帧还没解出来，而驱动方只等了两帧 rAF 就去截屏了 |
| **修法** | 三段等待：① 先 `__frame(t)` ② 算目标时刻 `want`，`|currentTime − want| < 0.04` 直接过，否则挂 `seeked` 事件 + 超时兜底 ③ 再等两次 rAF |
| **证据** | 补上等待后，成片里读到的时间码正好是 `00:01.000`（对应 t=1.0s）—— **帧级精确** |

> **通用教训**：同步驱动契约里一旦混进异步副作用（video / audio / font / 图片解码），
> **等待责任在驱动方**。只等帧回调是在赌"副作用比它快" —— 这种赌注平时会赢，关键时刻必输。

## 二、尺寸与几何

### 坑 05 · "4K" 只是外壳，画面还是 1080p

| | |
|---|---|
| **症状** | 产物文件确实是 3840×2160，**画面是 1920×1080 铺在左上角** |
| **真因** | 给一个按 1080p 设计的 DOM 页面直接传 `--w 3840`，CSS 布局按新视口重排，内容却没跟着放大 |
| **修法** | **视口保持设计尺寸 + `deviceScaleFactor=2` 超采样**（截图本身就是 3840×2160，不降采样） |
| **证据** | **文件尺寸判据照样 PASS** —— 这是判据盲区，只能靠"打开看一眼"（BUG-2395） |

### 坑 06 · 元素只露出右下 1/4，而 7 条判据全绿

| | |
|---|---|
| **症状** | 视频/元素偏在容器右下角，只露大约 1/4 |
| **真因** | `left:50%; top:50%` 把元素**左上角**钉到了容器中心，而 `transform: translate(x%,y%)` 里 `x=y=0` 的语义是"正好铺满"—— 两者叠加 |
| **修法** | 定位改 `left:0; top:0`；并**补一条几何判据** |
| **证据** | 当 7 条判据（显示/驱动/跟随/像素变化/fit/参考线/负控）**全绿**时，几何判据报**偏移 403.8 px** 红；修好后 **0.0 px** 绿（BUG-2693） |

> **教训**：几何类缺陷（偏移 / 缩放 / 裁切）**只能靠几何判据抓**。
> "有没有画面""动没动""像素变没变"这三类判据，永远抓不到"它在框里的什么位置"。

### 坑 07 · 调景辅助线烧进了成片

| | |
|---|---|
| **症状** | 成片上叠着三分线 + 四角括号 |
| **真因** | 辅助线默认开启（方便调景），**导出态没有任何一层拦它** |
| **修法** | **CSS 层兜底**：`body.export .guides { display:none !important }` —— 放 CSS 是因为导出的固化 HTML 会带上同一条规则，`!important` 能盖过 JS 内联样式 |
| **证据** | 细虚线在缩略图、亮度统计、帧率检查里**全都看不见**，只能抽帧放大看（BUG-2694） |

## 三、判据自己出错（最贵的一类）

### 坑 08 · 自己设的阈值，导致判据**假 PASS**

| | |
|---|---|
| **症状** | 判据全绿，但东西是坏的 |
| **真因** | 上限是我**拍脑袋填的 8070**，而真实的取值区间根本不包含这个数作为上限的意义 |
| **修法** | **阈值必须从真实分布量出来**，不能手填 |
| **证据** | 手填 8070 ⇒ 假 PASS |

### 坑 09 · 基准值手填，导致整轮结论**方向反了**

| | |
|---|---|
| **症状** | 报告说"比参考图差很多" |
| **真因** | 我手填参考图的 `p95 = 215`；**实测是 80 和 169** |
| **修法** | 基准值**必须能从产物复现**；写进文档的每个数都要能说出"怎么算出来的" |
| **证据** | 基准错 ⇒ 所有比较结论反向 |

> 这两条合起来是同一件事：**判据出错时，先怀疑判据自己。**
> 而且要自问一句：「**如果 bug 真的存在，这条判据会 FAIL 吗？**」

### 坑 10 · 恒 FAIL 的判据，照样通过了"注入故障验证"

| | |
|---|---|
| **症状** | 一条判据在正常数据上就报 FAIL（说明它本来就没法报绿），但它通过了"注入故障"测试 |
| **真因** | **注入只证明了它能报红，没证明它能报绿** |
| **修法** | 两件事都要验：① 正常输入 ⇒ PASS ② 注入故障 ⇒ FAIL |
| **证据** | 恒 FAIL 的判据在注入测试里"表现完美" |

### 坑 11 · A/B 的尺子坏了：Δ=0 的"完美绿灯"

| | |
|---|---|
| **症状** | 成片与预览逐像素比，Δ=0（完美通过）；两个**单变量负控**（画面明显不同）也只读出 0 和 2 |
| **真因** | 用了 `ffmpeg ... blend=all_mode=difference, scale=1:1` 取"平均差"。**这个量法对肉眼差异巨大的两张图几乎不敏感** |
| **修法** | 换 Python 逐像素（PIL + numpy，缩到 480×270 求平均绝对差） |
| **证据** | 实测基线：正常 **0.75** / 负控 **34.56** / **37.04**（BUG-2695） |

> **最严重的后果不是"判据松"** —— 判据松至少会报红。
> 而当时真实的缺陷是**"两边走了同一条错路"**（渲染窗口没拿到视频、页面侧也没注入），
> A/B 把这个**真实缺陷显示成了满分绿灯**。
>
> ⇒ **「Δ ≈ 0 太漂亮」本身就是一个必须追查的信号**：
> 先问"这两个东西是不是根本没有被区分开"。

## 四、执行与并发

### 坑 12 · `Promise.race` 不是 canceller

| | |
|---|---|
| **症状** | 加了超时，任务却"每片白等 299 秒" |
| **真因** | `Promise.race([任务, 超时])` 只是**不再等它**，任务本身还在跑 —— 资源没释放，下一片又要排队 |
| **修法** | 真要取消，必须取消**底层句柄**（`AbortController` / `kill` 子进程 / 关掉管道） |
| **证据** | 4K 每片白等 **299s**（BUG-2413） |

### 坑 13 · 同工程同时刻跑了两个渲染

| | |
|---|---|
| **症状** | 产物"基本正常"，只有某几帧是错的 |
| **真因** | 两个渲染进程抢同一份 `frames/` 目录，**互相覆盖中间帧** |
| **修法** | 一个工程同时刻只跑一个渲染；或每个进程写**独立**的临时帧目录 |
| **证据** | 几帧错、其余全对（BUG-2359） |

### 坑 14 · 改完代码，跑的却是旧产物 / 旧进程

| | |
|---|---|
| **症状** | "我明明改了，怎么还是老样子"；零报错 |
| **真因** | 验收的对象**不是本次的产物**。两种形态：① 中间产物/构建产物过期（缓存复用）② 端口上挂着上一轮留下的**孤儿进程**，测试连到了旧进程 |
| **修法** | **让验收对象自证身份**：产物带构建指纹（时间戳 + 内容 md5）并验新鲜度；进程连上后校验"你是从哪个路径起的" |
| **证据** | 构建指纹判据（`< 180 分钟`）+ 页面 URL 必须落在本次产物内 |

> **时间异常本身就是信号**：一次本该几十秒的测试只花了 **8 秒** —— 这个数字比任何日志都更早指向了"连错进程"。

## 五、度量与统计

### 坑 15 · 中间产物过期 = 静默假绿

| | |
|---|---|
| **症状** | 判据全绿，但那是**上一轮**的产物 |
| **真因** | 后一步没有校验前一步产物的新鲜度；`returncode == 0` 被当成了证据 |
| **修法** | 只认「**产物真写出** + **中间件验新鲜度**」。退出码 0 **不是**证据 |

### 坑 16 · 带 cadence 的对象，改了又被帧求值覆盖

| | |
|---|---|
| **症状** | 给某字段赋值后，下一帧又变回去了（"我改了没反应"） |
| **真因** | 那个字段是**每帧求值算出来的**，赋值只是改了"这一瞬间" |
| **修法** | 改完**回读断言**；真要持久，改的是它的**输入**而不是结果 |

### 坑 17 · 全局统计绿，局部一片空

| | |
|---|---|
| **症状** | 亮度/对比度/帧率统计全部正常，但某一整块区域是空的 |
| **真因** | **全局均值类判据对局部失效极不敏感**（一块空掉 20% 面积，全图均值可能只动几格） |
| **修法** | 用**分区/分块**判据，或者直接把多帧拼成一张接触印样用眼睛看 |

## 元结论

把上面 17 条按"能不能报错"分一下：

> **本项目实测统计：9 个典型缺陷里 8 个不会报错。**
> 唯一会报错的那个，反而是最好查的。

所以这套流程最后的形态是：

1. **能判的全部判**（`trial.js` 8 条红线 + 专项门禁）—— 而且每条都要**有牙**（故意做错一次，看它会不会红）
2. **判不到的那一类，留一关给眼睛** —— 把成片抽帧摊开，和页面预览做**同尺度 A/B**，逐像素比完再用肉眼看一遍

> 这两关缺一不可。**只有机器**，你会交出一堆"判据全绿但画面是错的"；
> **只有眼睛**，你会在 300 帧里漏掉第 217 帧。
